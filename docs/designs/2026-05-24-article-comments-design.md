# Article Comments Design

**Problem:** 前台文章详情缺少评论能力，未登录与已登录用户都无法按不同身份参与评论，后台也缺少面向管理员的评论管理入口。
**Solution:** 将评论设计为独立评论域，为文章提供可扩展的评论状态控制、前台展示与提交、本人删除与管理员删除、以及后台按文章筛选的评论管理能力。
**Out of scope:** 评论编辑、游客昵称或邮箱、评论审核流、评论回复/楼中楼、额外第三方评论组件。

## Technical Approach

- 为文章新增可扩展的评论状态枚举，当前先支持 `OPEN` 与 `CLOSED` 两态，后续可平滑扩展更多状态。
- 新增评论数据模型，评论必须归属某篇文章；登录用户评论关联个人账号并展示账号名；未登录用户评论记录为游客身份并统一展示“游客”。
- 前台文章详情默认展示评论区。文章评论状态为 `OPEN` 时显示评论列表和输入框；状态为 `CLOSED` 时隐藏输入框，并在评论区域展示“暂无评论”。
- 评论删除遵循权限规则：评论作者本人可以删除自己的评论；管理员可以删除任意评论；其他用户不可删除。
- 后台新增独立评论管理页面，仅管理员可见，支持按文章筛选、分页读取评论列表并执行删除。
- 评论能力采用独立服务层和接口层实现，与现有文章详情和后台文章管理能力解耦，避免把评论逻辑散落在文章服务中。

## Interface / Data Structures

### Article comment control

- `Article.commentStatus`: 评论状态枚举字段。
- 初始枚举值：`OPEN`、`CLOSED`。
- 前台只对 `OPEN` 状态允许提交评论。

### Comment entity

- `Comment.id`: 主键。
- `Comment.articleId`: 关联文章。
- `Comment.authorType`: 作者类型，区分 `GUEST` 与 `PERSONAL`。
- `Comment.personalUserId`: 登录用户评论时关联个人账号，游客评论为空。
- `Comment.body`: 评论正文。
- `Comment.createdAt` / `Comment.updatedAt`: 时间戳。

### Public-facing APIs

- 读取文章详情时附带评论状态与评论列表展示所需信息。
- 提供按文章读取评论列表接口，返回展示名、作者类型、正文、时间、当前用户是否可删除。
- 提供创建评论接口：
  - 游客允许直接提交正文。
  - 登录用户使用当前会话账号名作为展示名。
  - 文章状态非 `OPEN` 时拒绝创建。
- 提供删除评论接口：仅评论本人或管理员可执行。

### Admin APIs

- 提供管理员评论列表接口。
- 支持按文章 ID 筛选评论。
- 支持分页读取评论。
- 支持管理员删除任意评论。
- 提供文章评论状态更新能力，供后台文章详情或编辑流程控制评论开关。

## Edge Cases

- 文章不存在或未发布时，前台不暴露评论创建入口。
- 文章评论状态为 `CLOSED` 时，前台隐藏输入框，并统一展示“暂无评论”，不再渲染已有评论内容。
- 游客评论无额外昵称字段，所有游客评论统一显示“游客”，避免引入匿名身份管理复杂度。
- 登录用户删除评论时只能删除自己的评论，不能删除其他普通用户或游客评论。
- 管理员评论管理页只对管理员可见，个人用户与游客不可访问。
- 删除评论后，前台文章详情与后台管理列表需要读取最新数据，避免缓存显示旧评论。

## Acceptance Criteria

- [ ] 前台文章详情页支持展示评论区。
- [ ] 未登录用户可以以“游客”身份发表评论。
- [ ] 已登录用户发表评论时展示自己的账号名。
- [ ] 评论作者本人可以删除自己的评论。
- [ ] 管理员可以删除任意评论。
- [ ] 后台存在独立评论管理页面，且只有管理员可见。
- [ ] 后台评论管理页面支持按文章筛选评论。
- [ ] 文章支持评论状态控制，当前至少支持 `OPEN` 与 `CLOSED`。
- [ ] 文章评论状态为 `CLOSED` 时，前台隐藏评论输入框并显示“暂无评论”。
- [ ] 实现尽量不引入第三方库。
